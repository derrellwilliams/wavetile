## QA-3 security review — November 7, 2026 (in progress)

Reviewed Keychain/session storage, server transport classification and identity checks, API redirects, media request construction, podcast networking, feed parsing and OPML import. No personal credentials or live account data inspected.

- **Fixed: cross-origin credential-body redirects.** `RedirectGuard` previously removed only Authorization, permitting a redirected POST body (password or Quick Connect secret) to leave the original origin. It now refuses cross-origin requests unless they are body-free GET/HEAD requests, and refuses unknown origins. Same-origin login redirects and header-stripped CDN reads remain supported. Added regression cases for write methods, body streams and missing origins.
- **Fixed: OPML allocation before size check.** The importer previously loaded the whole file before enforcing its 5 MB limit. It now bounds the file read itself and closes the handle after use.
- **Storage:** tokens use device-only, after-first-unlock Keychain accessibility; session metadata uses UserDefaults. Keychain deletion errors are currently ignored on sign-out; assess failure/recovery semantics before closing this gate.
- **Transport:** remote HTTP sign-in is rejected; LAN HTTP remains intentionally allowed. Matching a public Jellyfin server ID helps detect a different machine after network changes but does not authenticate an HTTP peer against an active attacker. HTTPS remains necessary for that protection.
- **Media residual risk:** stream requests ask Jellyfin not to redirect, but this does not enforce origin restrictions against a reverse proxy. AVFoundation header behavior and background URLSession redirects require dedicated verification; the API redirect fix does not certify those paths.
- **Podcast parsing:** separate ephemeral networking disables cookies/credential storage; feed downloads have a 15 MB cap, XML external entity resolution is disabled, and feed/OPML URLs are filtered to HTTP(S). OPML entries are capped at 2,000 and episodes at 3,000. No claim of exhaustive malicious-XML/resource-exhaustion coverage.

Result: `build/Logs/Test/Test-WavetileKit-Package-2026.11.07_06-33-20--0700.xcresult`. Package build also compiled the changed Features importer. `git diff --check` passed. The documented iPhone 18 Pro destination was unavailable; use the installed Pro Max for this run.

**Contained follow-up — November 7:** added five hostile-input test cases (eight runs with parameterization): controlled temporary-file external entities cannot leak into feed titles or inject OPML subscriptions; oversized inputs retain at most 3,000 episodes / 2,000 subscriptions; OPML rejects file, JavaScript, data and app URL schemes while retaining a valid subscription. The file fixtures are generated by the tests and removed afterward; no user files are accessed. The initial run hit a Swift Testing macro evaluation issue with optional expressions; assigning concrete strings before assertions fixed the test harness, with no production parser change.

**Verification:** PodcastsTests passed on iPhone 18 Pro Max / iOS 27.0 (45 tests, 61 runs including parameterized cases, zero failures/skips). **Keychain failure review — November 7:** added an internal credential-store seam and five injected-failure tests; the public initializer still uses the real Keychain and runtime storage behavior is unchanged. Verified that failed deletion removes active-session metadata and prevents restoration even when the orphaned token remains readable; failed writes do not publish a new session or replace previous metadata; missing/unreadable tokens cannot restore a session; transient read errors preserve metadata for a later successful read. Tests use isolated UserDefaults suites and synthetic credentials, never the user's Keychain.

**Initial finding (local retry fixed below):** `SessionStore.clear()` ignored deletion errors and forgot the account needed to retry. The token can remain in Keychain, although it cannot independently restore a session. `AppModel.signOut()` also revokes remotely on a best-effort basis, so offline/unreadable-token sign-out cannot guarantee server invalidation. Follow-up: persist/retry failed local cleanup without permitting session restoration, test device lock/unlock behavior, and align the policy's unconditional token-removal wording if cleanup cannot be guaranteed. A transient read failure currently shows signed-out UI until another restore/relaunch; automatic unlock recovery was not tested.

**Keychain cleanup fix — November 7:** sign-out now queues the Keychain account identifier before clearing active-session metadata, and retries failed deletions on subsequent session loads, saves and clears. No token is copied to UserDefaults. A pending deletion blocks restoration even if clear was interrupted before metadata removal. Successful sign-in removes that account from pending cleanup after writing its replacement token; failed sign-in leaves cleanup pending. Added four regression tests for relaunch retry, replacement-token preservation, failed sign-in and interrupted clear.

## QA-3 media redirects and QA-2 playback/download review — November 7, 2026 (later)

**Superseded:** every edit in this section was compiled and tested later on Nov 7 (see the QA-4 section below: package 151/151, UI 17/17). **Not built or run when written:** this session's sandbox blocked `xcodebuild` (it can't write `~/Library/org.swift.swiftpm` or `~/Library/Developer/Xcode`), so the edits below are uncompiled and untested except the standalone helper check. Run the JellyfinKit, Library and Playback tests before committing.

- **Finding (fixed, containment only): background downloads can't stop a redirect.** Apple's `NSURLSession.h` states that tasks in background sessions always follow redirects and never call `willPerformHTTPRedirection`, so the `RedirectGuard` hook in `DownloadManager` never ran. The request carries the token in `Authorization`; whether CFNetwork strips it on a cross-origin redirect could not be tested here (the sandbox blocks local servers). Jellyfin already gets `enableRedirection=false`, so exposure needs a server or proxy that redirects off-origin anyway. Fix: the dead delegate method is removed; `DownloadManager` now checks where a task ended (`RedirectGuard.leftOrigin`) on completion and on failure. An off-origin result cancels all tasks, fails every pending download and skips the retry, so the token reaches one request, not every track and retry. Launch's retry-failed pass can re-queue them, so a persistent bad redirect still repeats once per launch. Standalone check of `leftOrigin` (5 origin cases plus nil URLs) passed; unit cases added to `RedirectGuardTests`.
- **Open (device): AVFoundation streaming redirects.** `AVURLAssetHTTPHeaderFieldsKey` header behavior on a redirect can't be intercepted in code. Verify by pointing the app at a reverse proxy that answers the audio request with a 302 to a second host that logs request headers; expect no `Authorization` there.
- **Privacy policy wording reconciled (local until the site is deployed):** sign-out removes the token, retries if iOS refuses, can't restore a session meanwhile, and server-side session end is best effort (revoke the device in the Jellyfin dashboard otherwise).
- **QA-2 finding (fixed, untested): endless skip loop.** When a track fails to play, `skipFailed` moved on, and under repeat-all `skipForward` wraps, so an expired sign-in or server error made the player cycle the queue forever, hammering the server in the background. It now stops after 10 failures in a row (or a full lap of a shorter queue); the count resets when something plays for a second, or when the listener starts a new queue or jumps. No `AudioPlayer` engine test exists for this; `PlaybackQueue` has tests.
- **Warning 1, AVAudioSession on the main thread (confirmed in code, not changed):** `activateSession()` and the `stop()` deactivation run on the main actor and discard errors with `try?`. Moving them off the main thread changes when `play()` starts relative to the category, which needs device verification first. Decision: keep as is for 1.0, log activation errors in a later change, and cover it in the device checklist (interruptions and route changes).
- **Warning 2, `Environment<Theme/Bool>` outside a View (cause not reproduced):** the only places that read both a `Theme` and a Bool environment value inside a style rather than a View are the custom `ButtonStyle`s (`TintedButtonStyle`, `TextButtonStyle`, `PressableButtonStyle`). Likely fix: have `makeBody` return a small View struct that holds the `@Environment` properties. Not applied without a build to confirm it silences the warning.
- **Reviewed, no issues found:** `DownloadManager` (header auth, file-name sanitizing, per-account protected folder, retry bounds), `EpisodeDownloadManager` (no Jellyfin headers or cookies; no size cap on enclosure downloads, low risk), `LibrarySync` prune guards, crash-prone constructs across the QA-2 modules (none: no `try!`, `fatalError`, forced casts or unwraps).

**Second pass, same day (uncompiled when written; compiled and run later, see the QA-4 section):** CarPlay, podcast sync and database, and the library editor.
- **`PodcastSync` (fixed): the server's copy was read without limits.** Only the upload was capped. A large or hostile preferences blob could queue thousands of sequential feed fetches (each up to 15 MB, to URLs the server chose) and apply unbounded positions. It is now read with the same limits: 2,000 subscriptions (the OPML ceiling), the 200 newest positions, 2,000 played dates, and negative positions dropped. Checked in a standalone compile (limits, newest-kept, round trip); `serverCopyIsReadWithLimits` added.
- **`PodcastDatabase` (fixed): an empty fetch pruned every unprotected episode.** A publisher glitch returning a feed with no items deleted all episodes without listening state. An upsert that saw no episodes now prunes nothing; `aFetchThatSawNoEpisodesPrunesNothing` added. Episodes with a position, saved, queued or downloaded were already protected, and migrations are additive with no erase-on-change.
- **`CarPlayController`: no defects found.** Created in `App.init`, so it works when CarPlay launches the app with no phone window; main-actor by the package's default isolation; database observation is debounced and unchanged lists aren't rebuilt. Two notes for the device pass: lists are cut at a fixed 200 rather than `CPListTemplate.maximumItemCount` (head units can allow fewer; confirm truncation is harmless), and if the Keychain can't be read at CarPlay launch the screen says "Sign in on your iPhone" until the app is relaunched (the same transient-read case recorded under QA-3).
- **`LibraryEditor`: no defects found.** Collection recreate creates before it deletes and reports a duplicate if cleanup fails. Notes: a rapid double favorite toggle where the first call fails reverts over the second; recreating a very large collection (over about 200 albums) may exceed the URL length at create, which fails before anything is deleted.
- **`Environment<Theme/Bool>` warning (change made, unconfirmed):** `TintedButtonStyle`, `TextButtonStyle` and `PressableButtonStyle` now return a private View that holds the `@Environment` reads, instead of reading them in the style. Layout, tokens and behavior are unchanged. A typecheck of the DesignSystem files against the iOS SDK showed no errors in `PrimaryButton.swift` or `Motion.swift` (the only errors were environmental: missing `Bundle.module`, blocked macro plugins, missing Inject and Nuke modules). Whether the warning is gone needs a debug run.
- **Left alone:** the `AVAudioSession` warning. No part of QA-2's module list remains unreviewed.

### Code review of the Nov 7 commits (medium, `fbe87ab..HEAD`)

Eight findings; each was checked against the code. Fixed: (1) an interruption `.began` could be followed by a still-queued `play()`, which would start audio mid-interruption, so `.began` now cancels the pending start; (2) `TrackSummary(item:)` (the API-backed path) lacked the blank-name, empty-artist and duration guards, so `ServerText`/`ServerDuration` moved to `JellyfinKit` (package-visible) and both paths share them, with `apiTrackSummariesGetTheSameFallbacksAndLimits` added. Not changed, with reasons: loop-one `player.play()` (session is already active while looping, and `stop()` clears the queue); extra latency and a double start in `resume()` (activation already ran on every track change; `resume()` loads before setting `isPlaying`, and a newer request supersedes the older one); `stop()` ordering (one serial queue keeps call order, every request bumps the token); an empty `SortKey` (the key is trimmed first, so what follows an article always has a non-space character); the one-time rewrite of rows with padded names (documented above; track, album, playlist and collection names all use the same helper); the `plain` flag on `TintedBarIcon` (style preference). Verification after the follow-up: package 151/151 (197 runs), UI 17/17 with no runtime warnings (`Test-Wavetile-2026.11.07_19-08-52--0700.xcresult`).

Source changes made to enable the tests (behavior otherwise unchanged): `migrator` is internal in `LibraryDatabase` and `PodcastDatabase`; artist, album and track mapping moved from inline closures into `ArtistRecord`/`AlbumRecord`/`TrackRecord` `init?(item:generation:)` in `Library/LibrarySync.swift`, with helpers in `Library/Mapping.swift`; `LibraryTests` now depends on `JellyfinKit`.

Defects found by reading the mapping code and fixed along the way:
- An empty `artists` array from the server gave a blank artist name instead of falling back to the album artist or "Unknown Artist". Blank or whitespace-only names (track, album, artist, playlist, collection) now fall back to the "Unknown …" placeholder; names are stored trimmed, so the next sync rewrites any row that had padding.
- Durations weren't bounded. Negative values are now 0 and anything over a year is capped, so summing a hostile playlist's entry durations can no longer overflow `Int` and trap. Negative play counts are 0.
- `SortKey.make("The  Beatles")` (two spaces) left a leading space, which sorted the item before everything else. The remainder is now trimmed.

Noted, not changed: a sync pass that sees a total of 0 returns an empty "seen" set, and the prune then deletes every row of that type. That is right for a truly empty library and costs only a resync otherwise (downloads live in their own tables), but a server that answers 200 with zero items would clear the cache. Not covered by a test because the behavior may be intended.

Still open for QA-4: nothing in scope. Migration tests for `downloadedTrack` bookkeeping beyond the v2 tables checked here are P2 with the download engine tests.

**Runtime warnings in the UI run, found and fixed the same day:** the first UI run showed `Accessing Environment<Bool>'s / Environment<Theme>'s value outside of being installed on a View` (about 17 each, so the Nov 7 `ButtonStyle` change had not been the cause) and `AVAudioSession_iOS.mm:978 … UI unresponsiveness if called on the main thread` (once).
- **Environment warning, cause found with a symbolicated backtrace** (`xcrun simctl spawn booted log stream --backtrace`, then `atos` against `Wavetile.debug.dylib`): `TintedSystemBack.Style.render()` drew the back chevron with `TintedBarIcon(glyph: .back).icon`, reading a computed property off a bare struct that was never installed in a view. Its `@Environment` reads (theme, enabled) therefore returned the defaults. This was a real defect, not only a warning: the chevron was drawn in the default Dark theme's accent whatever theme the app used, and `.environment(\.theme, theme)` applied afterward didn't reach it. Fix: `TintedBarIcon` has a `plain` mode that draws just the icon from its own `body`, the renderer uses that, and `icon` is private (`Features/Main/MainTabView.swift`). The Nov 7 `ButtonStyle` rewrite stays; it's harmless.
- **AVAudioSession warning, fixed (was "keep for 1.0").** `AudioPlayer` now sets the category and activates the session on one serial background queue and calls `player.play()` once activation completes, only if no newer request overtook it and the listener hasn't paused; `stop()` queues the deactivation on the same queue, so activate and deactivate keep call order. Now Playing and progress reporting follow `isPlaying`, so only the audio start waits for the session (typically milliseconds). **Not verified on a device:** interruptions, route changes, AirPlay and CarPlay still need the device pass (rows 23-29 in [carplay-device-checklist.md](carplay-device-checklist.md)); a start that never fires after an interruption is the failure to look for.

### R3-02 — High: collection rename can permanently lose server membership

`Library/LibraryEditor.swift:126–143` recreates a collection after a forbidden metadata update. `Library/LibrarySync.swift:281–293` stops after the first page when the total is absent and treats that page as complete (`total ?? 0`). ### R3-05 — High: logout deletes SQLite files while sync still owns the pool

`Features/LibraryStore.swift:49–58` creates an unstructured sync task that retains the store. `Features/AppModel.swift:159–178` neither cancels nor awaits it and unlinks SQLite/WAL/SHM files without closing the pool. - **No size cap or retry for episode downloads** (a failure waits for a manual retry). Low risk, as noted under QA-3.
- **Orphan episode files** from a crash between move and row update are not swept (same reasoning as music in section 4).
- **Podcast folder name** uses the non-injective ID sanitizing noted under R3 (section 8).

### R6-01 — High (fixed): sign-out deleted the podcast database while its store was still using it

R3-05 stopped the library's sync and closed its pool before deleting files, but the podcast database was unlinked with its pool open and its store still running: refresh and auto-download tasks, the debounced Jellyfin sync push, recommendations, and the ordered write queue (the player's final progress save from `player.stop()` runs there). Writes after sign-out landed in an unlinked file, and signing straight back in opened a second pool at the same path. `PodcastsStore.shutdown()` now stops new refreshes, syncs, pushes and writes, cancels and awaits the running ones, waits briefly for a sync already talking to the server, and closes the pool; `signOut()` runs it before the library's shutdown and before deleting anything, and fails the same way (session kept, alert shown) if a pool won't close.

### R6-02 — Medium (fixed): Siri's vocabulary only updated at launch

`WavetileShortcuts.updateAppShortcutParameters()` ran once in `WavetileApp.init`. A first-time user, whose library is empty at that launch, got no spoken names until a later launch after the first sync; and after signing out (or switching accounts) the previous account's album, artist and playlist names stayed in Siri's learned phrases until the next launch. `AppModel.onLibraryVocabularyChanged` now fires after each completed library sync, on sign-in and on sign-out; the app target points it at `updateAppShortcutParameters()`. Siri's lookups themselves were already empty when signed out.

### R6-03 — Medium (fixed): download Live Activities could be left frozen on the Lock Screen

The activity was updated by a task inside the process that started it. If iOS suspended or killed the app mid-download (the background session keeps downloading), nothing ever updated or ended the activity again, so it could show "Downloading 3 of 12" until the system's own limit, and sign-out didn't end it. `DownloadsStore` now ends activities this process isn't tracking when downloads are observed at launch, then re-attaches to downloads still running, ends all of them at sign-out, and keeps one activity per collection (a second Download or Retry tap during a run no longer starts another; this also closes the duplicate noted as deferred in section 4).

### R6-04 — Low (fixed): widgets could be repopulated after sign-out

`recentsChanged` fetches artwork for up to eight albums in a background task and then writes the Recently Played snapshot; one still running when the user signed out wrote the previous account's albums back after `WidgetStore.clear()`. A clear counter now makes such tasks stop before writing. A launch that comes up signed out (no saved session, a no-longer-allowed transport, or unusable storage) also clears the widgets instead of leaving the last session's snapshot and artwork on the Home and Lock Screens.

### R6-05 — Low (fixed): an odd album ID could crash the widget

`WidgetLink.album` built its URL with `URL(string:)!` from the server's album ID; an ID with a space or other URL-invalid character made the force unwrap trap in the widget extension. Unsafe characters are now percent-escaped (the app reads the same ID back from the last path component) with a fallback link instead of a crash.

Widget and Lock Screen controls (`AudioPlaybackIntent`) forward only play/pause and next through a handler the signed-in app registers; with no session they do nothing. App group data is two small JSON files and artwork, no tokens or server addresses, removed at sign-out. Siri: names and playback come from the local database, nothing is sent anywhere by the app, and entities are looked up by ID so a stale Shortcut for a deleted item fails with "Couldn't play". CarPlay: shows an "Open Wavetile on your iPhone" screen if the app isn't ready, plays through the same queue as the phone (offline, only downloaded songs), and refreshes lists in place. ## Targeted review 8 — cross-subsystem scenarios — 2026-11-07

Scenarios traced end to end through the code already reviewed in sections 1–7, looking for steps where one subsystem's cleanup or failure leaves another inconsistent.

| Scenario | Result |

| Sign out during a download | Fixed across R3-05, R4-01, R5-04, R6-01, R6-03: sync and podcast work stop and both databases close before any file is deleted, the music and podcast sessions are invalidated, Live Activities end, widgets clear (and late widget writes are dropped), Siri's vocabulary refreshes. ### R8-01 — Medium (fixed): a failed database open could delete freshly downloaded files

When a library or podcast database can't be opened (a failed migration, a full disk), `makeSignedIn` runs the session on an empty temporary database but still created the download managers. If iOS relaunched the app at that moment to deliver finished background downloads, each completed file had no row, `updateDownload` reported "no longer wanted", and the file was deleted (the same rule that cleans up after a removed download). The user also saw their library, downloads and podcast state apparently gone, with nothing in the logs. `LibraryDatabase` and `PodcastDatabase` now know when they are the stand-in (`isTemporary`), the download managers are not created against them (nothing is saved or deleted; the system keeps the finished transfers until a normal launch), and the fallback is logged as a fault with the error. The real database file is untouched, so the next launch that opens it shows everything again.

### Deferred, with rationale

- **Account identity in file names:** database, download and podcast folder names strip characters from the server and user IDs and join them. Real Jellyfin IDs are 32-character GUIDs and never collide, but two servers cloned from the same configuration share a server ID, so one user ID on both would share a database and download folder. Namespacing by server address would orphan every existing install's data and needs a migration; recommended after launch if cloned-server reports appear.
- **Silent fallback visibility:** apart from the new log entry, the user isn't told when a database couldn't open. A banner or an "your library couldn't be opened" screen is a product decision.
- **Interrupted sign-out** leaves the session in place (credentials are cleared last) and the user repeats it; the alternative order would leave account data on disk once credentials are gone.
- **A manual refresh killed mid-sync** isn't retried before the one-hour freshness window ends.
